TorchTPU: Bringing Native PyTorch to Google TPUs

原文：[Introducing TorchTPU - PyTorch](https://pytorch.org/blog/introducing-torchtpu/)

摘要

TorchTPU 是 Google 与 Meta 合作开发的开源 PyTorch TPU 后端，目标是让现有工作负载先以较少改动运行，再按 TPU 的特点优化。节目解释了它的急切执行与 DeferAndFuse 模式、编译缓存、视图语义、精度选择，以及分布式通信如何接入 PyTorch。文章报告了模型兼容性测试、纯 PyTorch 工作负载的性能和大规模训练的扩展结果，但这些结果对应不同的测试范围。动态形状、部分分布式性能优化和单进程设备限制仍是后续工作。

对话

Ava: If your training code is already PyTorch, moving it to a TPU raises a practical question: how much of the program has to change? TorchTPU matters because it aims to make a Google TPU feel like a native PyTorch device.

Ava：如果你的训练代码已经用 PyTorch 编写，迁移到 TPU 时会遇到一个实际问题：程序究竟要改多少？TorchTPU 的价值在于，它希望让 Google TPU 像 PyTorch 的原生设备一样使用。

Brian: And that promise goes beyond moving a model. TorchTPU supports eager execution, torch.compile, and PyTorch distributed APIs. That gives teams a path to run familiar code first, then tune the parts that need to fit TPU hardware better.

Brian：而且这一承诺不只是让模型能在 TPU 上运行。TorchTPU 支持即时执行、torch.compile 和 PyTorch 分布式 API。这样，团队可以先运行熟悉的代码，再调整那些需要更好地适配 TPU 硬件的部分。

Ava: The motivation makes sense. PyTorch/XLA brought compiled PyTorch to TPUs, but its Lazy Tensor approach didn't support PyTorch's native eager mode. It also required explicit changes to mark compilable regions. That's a serious migration cost for an existing training stack.

Ava：这个出发点很合理。PyTorch/XLA 让编译式 PyTorch 能在 TPU 上运行，但它采用的 Lazy Tensor 方式不支持 PyTorch 原生的即时执行模式。它还要求显式修改代码，标出可编译的区域。对于现有训练系统来说，这是很高的迁移成本。

Brian: Right. The project started at Google in mid-2025 with the PyTorch team at Meta. Its design puts eager mode and existing PyTorch idioms first. The goal is that a workload can start by changing its device from CUDA to TPU, even if peak performance takes more work.

Brian：没错。这个项目由 Google 和 Meta 的 PyTorch 团队于 2025 年年中启动。它在设计上优先支持即时模式和现有的 PyTorch 编程习惯。目标是让工作负载只需把设备从 CUDA 改成 TPU 就能开始运行，即使要达到峰值性能还需要进一步调整。

Ava: Let's make that concrete. For a single-device model, the change can be as small as moving it with model.to("tpu") instead of model.to("cuda"). But shapes, sharding, and operators chosen for a GPU may still be poor choices for a TPU.

Ava：说具体一点。对于单设备模型，改动可能只需把 model.to("cuda") 换成 model.to("tpu")。但为 GPU 选定的张量形状、分片方式和算子，对 TPU 来说仍可能是不合适的选择。

Brian: Exactly. TorchTPU uses PyTorch's autoload mechanism when its wheel is installed on a TPU machine. For distributed code, the example changes the process group backend from nccl to tpu_dist. It also shows a device-neutral option through torch.accelerator.current_accelerator().

Brian：正是如此。在 TPU 机器上安装 TorchTPU 的 wheel 包后，它会使用 PyTorch 的自动加载机制。对于分布式代码，示例把进程组后端从 nccl 改为 tpu_dist。示例还展示了通过 torch.accelerator.current_accelerator() 实现的不依赖特定设备的写法。

Ava: Before the software details, the hardware explains some of those tuning choices. A TPU TensorCore has large matrix units, while a SparseCore can handle sparse work and collectives. So a model's matrix shapes and communication pattern can matter as much as its device string.

Ava：在谈软件细节之前，先看看硬件，就能理解其中一些调优选择。TPU TensorCore 有大型矩阵单元，而 SparseCore 可以处理稀疏计算和集合通信。因此，模型的矩阵形状和通信模式可能和设备字符串一样重要。

Brian: Yes. The matrix-multiply units, or MXUs, need sufficiently wide shapes to reach their potential. Underneath TorchTPU, XLA compiles StableHLO programs, and PjRT launches the resulting executables. TPU work is asynchronous, so the CPU can keep going until it needs a result.

Brian：是的。矩阵乘法单元，也就是 MXU，需要足够宽的形状才能发挥潜力。在 TorchTPU 底层，XLA 编译 StableHLO 程序，PjRT 启动生成的可执行程序。TPU 工作是异步的，所以 CPU 可以继续运行，直到需要计算结果。

Ava: That brings us to eager execution. I usually expect one PyTorch operator to be dispatched at a time. TorchTPU keeps that option, but it can also hold operators back and compile a larger group when a result has to be materialized.

Ava：这就说到了即时执行。我通常认为 PyTorch 会一次分发一个算子。TorchTPU 保留了这种方式，但它也可以暂缓执行算子，等到必须把结果实体化时，再将更大的一组算子一起编译。

Brian: Strict is the default eager mode: it dispatches one ATen operator at a time, asynchronously. Debug mode makes those launches synchronous and enables bound checks. DeferAndFuse is the hybrid mode. It groups deferred operators and can be 50% or more faster than Strict, while reducing peak HBM use.

Brian：Strict 是默认的即时模式：它每次异步分发一个 ATen 算子。Debug 模式会让这些启动操作同步进行，并启用边界检查。DeferAndFuse 是混合模式。它会把延迟执行的算子分组，速度可以比 Strict 快 50% 或更多，同时降低 HBM 峰值用量。

Ava: There's a catch. If execution waits until a value goes back to the CPU, wouldn't the TPU sit idle while Python builds the deferred work? A transformer stack might repeat the same pattern many times before that transfer.

Ava：但这里有个问题。如果执行一直等到某个值传回 CPU 才开始，那么 Python 构建延迟执行任务时，TPU 不就会闲着吗？在发生这次传输前，一个 Transformer 模块堆栈可能会多次重复同一种模式。

Brian: That's why TorchTPU also has a Repeated Ops Heuristic. It can trigger materialization before a TPU-to-CPU transfer. The team expects the compilation cache to fill after the first few steps, leaving CPU tracing and dispatch ahead of longer TPU computations in typical workloads.

Brian：所以 TorchTPU 还有一个 Repeated Ops Heuristic。它可以在 TPU 向 CPU 传输数据之前触发实体化。团队预计，经过最初几步后，编译缓存就会填充起来；在典型工作负载中，CPU 的追踪和分发便能领先于耗时更长的 TPU 计算。

Ava: And when materialization happens, it isn't simply every operator seen so far. TorchTPU checks which deferred operations contribute to the requested value. It preserves side effects, including collectives and their order. That sounds important for correctness across replicas.

Ava：而且，发生实体化时，并不是把此前见到的每个算子都执行一遍。TorchTPU 会检查哪些延迟执行的操作会影响请求的值。它还会保留副作用，包括集合通信及其执行顺序。这听起来对多个副本之间的正确性很重要。

Brian: It is. TorchTPU then looks for a compiled executable in its cache. The first tier is in process memory. A second tier can share serialized executables across processes on one machine, and a third can persist them across hosts or job restarts. That third tier needs an explicit shared storage path.

Brian：确实如此。接着，TorchTPU 会在缓存中查找编译好的可执行程序。第一层是进程内存。第二层可以让同一台机器上的多个进程共享序列化后的可执行程序，第三层可以让它们在不同主机之间或作业重启后继续保留。第三层需要显式指定共享存储路径。

Ava: Caching helps compile time, but semantics are another hurdle. In PyTorch, two tensor views can share storage, and an in-place write through one view becomes visible through the other. StableHLO treats values as immutable. How does TorchTPU bridge that difference?

Ava：缓存有助于减少编译时间，但语义是另一道难关。在 PyTorch 中，两个张量视图可以共享存储空间，通过一个视图进行的原地写入会通过另一个视图体现出来。StableHLO 把值视为不可变的。TorchTPU 如何弥合这种差异？

Brian: It uses view decomposition, view inversion, and deferred operations to preserve PyTorch view behavior. The detail matters because changing a device should preserve the result of existing code, including writes through views. The article points to concatenated parameter arrays in distributed training as one useful pattern this supports.

Brian：它通过视图分解、视图逆变换和延迟执行操作来保留 PyTorch 的视图行为。这个细节很重要，因为更换设备后，现有代码的结果应该保持一致，包括通过视图进行写入的结果。文章举出的一个受益场景是分布式训练中的拼接参数数组。

Ava: Precision has a similar migration issue. A program may say FP32, but TPU matrix multiplication is built around BF16 inputs. I'd want to know what arithmetic actually runs before comparing convergence or speed.

Ava：精度也有类似的迁移问题。程序可能写的是 FP32，但 TPU 矩阵乘法主要使用 BF16 输入。在比较收敛情况或速度之前，我会想知道实际执行的是什么运算。

Brian: TorchTPU defaults to medium precision for matrix multiplication: BF16 multiplication with FP32 accumulation. Its high mode uses 3 passes to recover most FP32 precision, at roughly 3 times the MXU compute cost. Highest uses 6 passes for an approximation of full IEEE FP32 accuracy, at roughly 6 times the compute cost.

Brian：TorchTPU 的矩阵乘法默认使用 medium 精度：以 BF16 做乘法，以 FP32 做累加。high 模式通过 3 轮计算恢复大部分 FP32 精度，MXU 计算成本约为 3 倍。highest 模式通过 6 轮计算来近似完整的 IEEE FP32 精度，计算成本约为 6 倍。

Ava: That distinction matters. The precision modes describe matrix multiplication, while non-contracting FP32 operations run on the vector unit. So the article recommends medium by default, with higher precision reserved for an identified convergence problem.

Ava：这个区别很重要。这些精度模式描述的是矩阵乘法，而不进行乘加融合的 FP32 运算在向量单元上运行。因此，文章建议默认使用 medium，只在发现收敛问题时才使用更高精度。

Brian: And there are two controls. The global PyTorch setting is torch.set_float32_matmul_precision. TorchTPU also offers the thread-local torch.tpu.precision context manager for a sensitive section. Selecting high or highest triggers a performance warning, which makes that cost harder to miss.

Brian：而且有两种控制方式。PyTorch 的全局设置是 torch.set_float32_matmul_precision。TorchTPU 还提供线程局部的 torch.tpu.precision 上下文管理器，可用于对精度敏感的代码段。选择 high 或 highest 会触发性能警告，让人更难忽略其开销。

Ava: Now suppose the eager path works and I want a larger compiled graph. TorchTPU uses torch.compile with the tpu backend. Does that go through the usual PyTorch compiler front end, or does it bring back Lazy Tensors?

Ava：假设即时执行路径已经跑通，而我想要一个更大的编译图。TorchTPU 使用以 tpu 为后端的 torch.compile。它走的是常规的 PyTorch 编译器前端，还是又用回了 Lazy Tensors？

Brian: It goes through Dynamo. TorchTPU traces the graph with its operations deferred, produces one StableHLO program for that graph, compiles it, and returns a callable that launches the TPU executable. The trade-off is that dynamic shape support is still being developed; torch.compile currently sets dynamic to false on a TPU machine.

Brian：它走的是 Dynamo。TorchTPU 在延迟执行图中操作的情况下追踪计算图，为该图生成一个 StableHLO 程序并将其编译，然后返回一个可调用对象来启动 TPU 可执行程序。取舍在于，动态形状支持仍在开发中；目前在 TPU 机器上，torch.compile 会把 dynamic 设为 false。

Ava: So a changing sequence length is still a real engineering concern. What happens when the shape varies between steps? Traditional XLA compilation assumes shapes are known, and manually padding to a larger size adds work to the model code.

Ava：所以，序列长度变化仍然是一个切实的工程问题。如果每一步的形状都不同，会发生什么？传统的 XLA 编译假定形状已知，而手动填充到较大的尺寸又会增加模型代码的工作量。

Brian: The planned answer is bounded dynamism. The compiled graph allocates a buffer using a known upper bound, while the actual logical size can vary at runtime. XLA handles padding and slicing without recompiling for each change. TorchTPU is actively developing this support, and it isn't enabled by default for torch.compile yet.

Brian：计划中的解决方案是有界动态性。编译后的计算图使用已知的上限分配缓冲区，实际的逻辑大小则可以在运行时变化。XLA 处理填充和切片，无须为每次变化重新编译。TorchTPU 正在积极开发这项支持，但它尚未成为 torch.compile 的默认功能。

Ava: Distributed training adds another test of whether this really feels like PyTorch. DTensor and FSDP expect collectives through familiar framework APIs. But TPU collectives live inside StableHLO programs, so the backend has to connect those two worlds.

Ava：分布式训练又是一个检验：它用起来是否真的像 PyTorch？DTensor 和 FSDP 预期通过熟悉的框架 API 来执行集合通信。但 TPU 的集合通信位于 StableHLO 程序内部，所以后端必须把这两者连接起来。

Brian: TorchTPU implements collectives at the Process Group API level, including support for eager and compiled execution. It uses one process per device. By default, it compiles each collective into its own small StableHLO module, called a Skinny Collective. That keeps communication consistent when different ranks execute different model operations.

Brian：TorchTPU 在 Process Group API 层实现集合通信，同时支持即时执行和编译执行。它采用每个设备一个进程的方式。默认情况下，它会把每个集合通信操作编译成一个独立的小型 StableHLO 模块，称为 Skinny Collective。这使不同 rank 执行不同模型操作时，通信仍能保持一致。

Ava: The cost is less room for XLA to overlap communication with computation. The article gives an example of a 30–40% end-to-end penalty. If a region is genuinely the same across ranks, can the compiler keep collectives inside a larger graph?

Ava：代价是 XLA 能将通信与计算重叠执行的空间变小了。文章给出的一个例子中，端到端性能损失为 30–40%。如果某个代码区域在各个 rank 上确实相同，编译器能否把集合通信留在更大的计算图里？

Brian: Yes, with the optional spmd_safe decorator. It lets torch.compile avoid graph breaks around collectives in a section the user knows is SPMD. But that promise is the user's responsibility; rank-dependent work can be subtle. A compilation handshake that checks graph agreement across replicas is proposed as another route.

Brian：可以，使用可选的 spmd_safe 装饰器即可。对于用户确认符合 SPMD 的代码段，它允许 torch.compile 避免在集合通信操作周围中断计算图。但确保这一点是用户的责任；依赖 rank 的操作可能很隐蔽。另一条提出的路径是进行编译握手，检查各个副本的计算图是否一致。

Ava: That leaves room for hardware-specific tuning without making it mandatory for every model. TorchTPU can connect custom Pallas kernels to PyTorch, and it supports kernels from Tokamax. Helion is another option, though the article calls that path experimental.

Ava：这给针对硬件的调优留出了空间，又不会要求每个模型都必须这么做。TorchTPU 可以把自定义 Pallas 内核接入 PyTorch，也支持来自 Tokamax 的内核。Helion 是另一个选择，不过文章称这条路径仍处于实验阶段。

Brian: In practice, that split is useful. Standard PyTorch operations can get a workload running. Pallas kernels can target a costly part of the model, including communication over the TPU interconnect. The article's large-scale training example does use specialized kernels, so its numbers shouldn't be read as pure out-of-box performance.

Brian：实际使用时，这种分工很有帮助。标准 PyTorch 算子可以先让工作负载跑起来。Pallas 内核则可以针对模型中开销较大的部分，包括通过 TPU 互连进行的通信。文章中的大规模训练示例确实使用了专用内核，因此不能把它的数字理解为完全开箱即用的性能。

Ava: Let's look at the evidence in layers. The model coverage study tested 4,917 Hugging Face models. Its first question was whether models could run and compile without crashing. Numerical agreement with a GPU baseline was checked on a smaller architectural set.

Ava：我们分层看看证据。模型覆盖率研究测试了 4,917 个 Hugging Face 模型。它首先检查模型能否运行并完成编译而不崩溃。与 GPU 基线的数值一致性则是在一个较小的架构集合上检查的。

Brian: For the popularity set, 4,821 of 4,917 models passed the no-crash check, or 98%. In the architecture set, 638 of 657 representative models met the numerical parity test, or 97%. Separately, bounded dynamism testing found correct numerics on 834 of 839 causal language models. Those are different checks with different scopes.

Brian：在按受欢迎程度选取的模型集合中，4,917 个模型里有 4,821 个通过了无崩溃检查，占 98%。在架构集合中，657 个代表性模型里有 638 个通过了数值一致性测试，占 97%。另外，有界动态性测试发现，839 个因果语言模型中有 834 个得到了正确的数值结果。这些是范围各不相同的检查。

Ava: The pure PyTorch performance example answers a different question: can standard modules and collectives make good use of a TPU without model-specific custom kernels? The authors used a Muse Glimmer 30B implementation and reported both inference prefill and training results.

Ava：纯 PyTorch 性能示例回答的是另一个问题：不使用针对特定模型的自定义内核，标准模块和集合通信能否充分利用 TPU？作者使用了 Muse Glimmer 30B 的一种实现，并报告了推理预填充和训练的结果。

Brian: At a sequence length of 5,120, prefill on one TPU v7 chip reached about 25,700 tokens per second at 59% MFU. That prefill run used FSDP with a world size of 2, because the chip exposes two TensorCores as separate PyTorch devices. Training on 4 TPU v7 chips reached about 5,600 tokens per second per TPU at 38% MFU. The training setup used FSDP and activation checkpointing, so those choices belong with the numbers.

Brian：在序列长度为 5,120 时，单个 TPU v7 芯片上的预填充速度约为每秒 25,700 个 token，MFU 为 59%。这次预填充运行使用了 FSDP，world size 为 2，因为该芯片将两个 TensorCore 作为独立的 PyTorch 设备暴露出来。在 4 个 TPU v7 芯片上训练时，每个 TPU 的速度约为每秒 5,600 个 token，MFU 为 38%。训练配置使用了 FSDP 和激活检查点，因此解读这些数字时也应考虑这些设置。

Ava: The scale test is more specialized. It trained a Qwen3 MoE 235B model with TorchTitan, using Pallas kernels and several training optimizations. As the run grew from 1 to 8 slices, the batch size grew too. That's a weak-scaling test.

Ava：规模测试的配置更专门化。它用 TorchTitan 训练了一个 Qwen3 MoE 235B 模型，使用了 Pallas 内核和多项训练优化。随着运行规模从 1 个切片扩大到 8 个切片，批量大小也随之增加。这是一项弱扩展性测试。

Brian: Across those endpoints, the setup went from 1,024 to 8,192 TPU v7 chips. Throughput per TensorCore went from 2,236 to 2,104 tokens per second, while MFU went from 28.8% to 27.1%. The article attributes the nearly flat per-core throughput in part to overlapping cross-slice gradient all-reduce with computation.

Brian：在这两个端点之间，配置从 1,024 个 TPU v7 芯片扩大到 8,192 个。每个 TensorCore 的吞吐量从每秒 2,236 个 token 变为 2,104 个，MFU 从 28.8% 变为 27.1%。文章认为，每个核心的吞吐量几乎保持不变，部分原因是跨切片梯度 all-reduce 与计算重叠执行。

Ava: So I'd separate the takeaways. Compatibility has broad test coverage, a standard PyTorch model has measured TPU performance, and a tuned training stack has shown weak scaling. It depends on the workload. What should an engineer watch as TorchTPU develops?

Ava：所以我会把结论分开看。兼容性有广泛的测试覆盖，一个标准 PyTorch 模型有实测的 TPU 性能，而一套经过调优的训练系统展现了弱扩展性。具体情况取决于工作负载。随着 TorchTPU 的发展，工程师应该关注什么？

Brian: Watch bounded dynamism in torch.compile, better overlap for Skinny Collectives, and the TPU limit that allows only one user-space process per device, which complicates colocated reinforcement-learning workloads. For now, the useful path is clear: try the familiar PyTorch workload, check its numerics, then profile the shapes and communication. Thanks for listening.

Brian：关注 torch.compile 中的有界动态性、Skinny Collectives 在通信与计算重叠执行方面的改进，以及 TPU 每个设备只允许一个用户空间进程的限制；这一限制使强化学习工作负载的同机部署更加复杂。目前，可行的路径很明确：先试运行熟悉的 PyTorch 工作负载，检查数值结果，再分析张量形状和通信性能。感谢收听。

术语

Term · 释义

eager execution · 按程序执行顺序处理操作的 PyTorch 执行方式。

Lazy Tensor · 延后操作执行、积累计算图的张量机制。

DeferAndFuse · TorchTPU 将多个延后执行的操作合并编译的模式。

materialization · 将延后计算的结果实际生成出来。

StableHLO · 供 XLA 编译的机器学习操作中间表示。

PjRT · 用于编译、启动 TPU 可执行程序及传输数据的运行时接口。

MXU · TPU 的矩阵乘法单元。

BF16 · TPU 矩阵乘法使用的 bfloat16 数据格式。

bounded dynamism · 编译时确定维度上界、运行时允许实际维度变化的机制。

Skinny Collective · 单独编译成小型 StableHLO 模块的集合通信操作。

weak scaling · 增加设备时同步增加总工作量，观察每个设备的处理能力能否维持。

中文内容总结

TorchTPU 是 Google 与 Meta 合作开发的开源项目，让 PyTorch 模型以较小改动运行在 Google TPU 上，同时支持即时执行、torch.compile 和分布式训练。项目仍在开发中，文中报告了模型兼容性及部分训练、推理结果。

要解决的问题

此前的 PyTorch/XLA 依赖 Lazy Tensor，常需修改代码来划定编译区域，编译延迟较高，也缺少原生即时执行支持。TorchTPU 以 PyTorch 后端的方式接入 TPU。简单模型可将设备从 cuda 改为 tpu；分布式示例使用 tpu_dist，文中也给出不显式指定后端的初始化写法。运行分布式程序还需配置 TPU 拓扑。能运行不等于达到最佳性能。

执行与编译机制

TorchTPU 通过 PyTorch 调度器接收 ATen 算子，将其转换为 StableHLO，再由 XLA 编译、PjRT 执行。StableHLO 不支持共享视图和原位修改，TorchTPU 通过视图分解、视图逆变换及延迟算子保留相应的 PyTorch 语义。默认 Strict 模式逐算子异步提交；DeferAndFuse 延后并融合算子，作者称可比 Strict 快 50% 或更多，并降低峰值 HBM 占用。编译缓存支持进程内、同机跨进程及可选的持久化复用。torch.compile 使用 Dynamo 前端；有界动态形状仍在开发，因此目前会自动设置 dynamic=False。

精度与分布式

矩阵乘法默认采用 BF16 输入、FP32 累加的 medium 模式；high 和 highest 分别用约 3 倍、6 倍的 MXU 计算量换取更高精度。TorchTPU 在 Process Group 层实现 TPU 集合通信，支持 DTensor 等 PyTorch 用法，并采用每设备一进程。为避免各进程的通信程序不一致，默认将集合操作单独编译；与把通信嵌入较大 StableHLO 模块、使其同计算重叠的方式相比，作者称这在一些场景可能带来约 30% 至 40% 的端到端性能损失。

兼容性验证

项目测试了 4,917 个 Hugging Face 模型，其中 4,821 个通过无崩溃测试，比例为 98%；657 个架构代表模型中，638 个达到相对 GPU 基线的数值一致性标准，比例为 97%。有界动态形状的数值测试覆盖了上述模型语料中的 839 个因果语言模型，其中 834 个结果正确。这些指标分别衡量运行稳定性和特定阈值下的数值结果，不能等同于所有模型都已达到最佳性能。

训练性能

在无需模型专用内核的 Muse Glimmer 30B 示例中，单块 TPU v7 使用 FSDP、world size 为 2，序列长度 5,120 时预填充达到约 25.7k token/s、59% MFU；四块 TPU v7 启用激活检查点后，在相同序列长度下训练达到每块约 5.6k token/s、38% MFU。Qwen3 MoE 235B 的 TorchTitan 扩展测试采用每 TensorCore 批量 16、序列长度 4,096；单个 slice 用 FSDP，多个 slice 用 HSDP。从 1,024 扩至 8,192 块 TPU v7 时，每个 TensorCore 的吞吐量由 2,236 降至 2,104 token/s，MFU 由 28.8% 降至 27.1%。作者据此称整体吞吐量近线性增长，呈现弱扩展。该测试还使用 Pallas 内核、混合精度和激活检查点等优化。

推理与实际限制

文章引用 SemiAnalysis 的 InferenceX 8K/1K 评测，报告 Qwen3.5 推理成本为每百万 token 2.01 美分；Google 提交的 AgentX 四块 TPU v7 测试结果为每百万 token 0.83 美分。这些结果依赖定制 Pallas 内核及运行时调优。自定义内核可通过 Pallas、Tokamax 或实验性的 Helion 接入。TPU 的单进程设备限制、动态形状支持和部分尚未支持的算子，仍会影响现有程序迁移。
