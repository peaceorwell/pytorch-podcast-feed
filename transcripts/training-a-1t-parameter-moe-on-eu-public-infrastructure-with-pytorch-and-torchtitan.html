Training a 1T-Parameter MoE on EU Public Infrastructure with PyTorch and TorchTitan

原文：[Training a 1T-Parameter MoE on EU public infrastructure with PyTorch and TorchTitan - PyTorch](https://pytorch.org/blog/training-a-1t-parameter-moe-on-eu-public-infrastructure-with-pytorch-and-torchtitan/)

摘要

这篇文章介绍了 EUROPA 联盟如何在共享的欧洲公共基础设施 JUPITER 上训练约一万亿参数的 MoE 模型。通过 FlexShard、Muon 的 GPU 优化器执行、激活检查点卸载，以及改进 FSDP 的异步 all-gather，他们把吞吐从每 GPU 每秒 90 个 token 提升到约 1,300 个 token。文章还解释了 GH200 的 HBM、Grace 内存和 InfiniBand 带宽限制如何决定并行布局。最终配置在四个数据并行副本上使用 1,536 张 GPU，并将修复和改进上游到 PyTorch 与 TorchTitan。

对话

Ava: We’ll focus on how the EUROPA consortium made trillion-parameter MoE training workable on shared public infrastructure.

Ava：我们将重点讨论 EUROPA 联盟如何在共享的公共基础设施上，让万亿参数 MoE 训练变得可行。

Brian: The key result is a rise from 90 to about 1,300 tokens per second per GPU, using 384 NVIDIA GH200 GPUs per data-parallel replica, across 96 nodes.

Brian：关键结果是吞吐量从每块 GPU 每秒 90 个 token 提升到约 1,300 个 token；在 96 个节点上，每个数据并行副本使用 384 块 NVIDIA GH200 GPU。

Ava: This result came from the EuroHPC Frontier AI Grand Challenge, which aimed to show that sovereign, open-source AI could compete at frontier levels on shared public resources.

Ava：这一成果来自 EuroHPC Frontier AI Grand Challenge，其目标是证明主权级开源 AI 能够在共享公共资源上达到前沿水平。

Brian: The EUROPA consortium was selected for a project requiring an open European MoE model of at least 400B parameters, support for all 24 official EU languages, and strict compliance with the EU AI Act.

Brian：EUROPA 联盟被选中执行一个项目，该项目要求构建至少拥有 400B 参数的开放式欧洲 MoE 模型，支持欧盟全部 24 种官方语言，并严格遵守《欧盟人工智能法案》（EU AI Act）。

Ava: That matters because JUPITER is publicly funded research infrastructure shared by hundreds of projects, rather than a cluster reserved for one model developer.

Ava：这很重要，因为 JUPITER 是由公共资金资助、供数百个项目共享的科研基础设施，而不是为某个模型开发者预留的集群。

Brian: JUPITER is the EuroHPC exascale supercomputer hosted at Forschungszentrum Jülich. The model has 951.9 billion total parameters, with 32.8 billion active per token, 74 layers, 384 routed experts with top-8 routing, a hidden size of 6,144, a vocabulary of 256,000, and a pretraining sequence length of 65,536 tokens.

Brian：JUPITER 是由 Forschungszentrum Jülich 托管的 EuroHPC 百亿亿次级超级计算机。该模型总参数量为 9519 亿，每个 token 激活 328 亿个参数，包含 74 层、384 个路由专家并采用 top-8 路由，隐藏维度为 6,144，词表大小为 256,000，预训练序列长度为 65,536 个 token。

Ava: And the optimizer is Muon plus AdamW, which becomes important because optimizer state takes a lot of memory at this scale.

Ava：此外，优化器是 Muon 加 AdamW；这一点很重要，因为在这种规模下，优化器状态会占用大量内存。

Brian: Each JUPITER Booster node has four NVIDIA GH200 Grace Hopper Superchips. Each superchip pairs a Hopper GPU with 96 GB of HBM3 and a 72-core Grace CPU with 120 GB of LPDDR5X, connected by a 900 GB/s NVLink-C2C link.

Brian：每个 JUPITER Booster 节点包含 4 个 NVIDIA GH200 Grace Hopper Superchips。每个 Superchip 都将一块配备 96 GB HBM3 的 Hopper GPU 与一颗配备 120 GB LPDDR5X 的 72 核 Grace CPU 配对，并通过 900 GB/s 的 NVLink-C2C 链路连接。

Ava: Inside a node, GPUs connect through NVLink 4 at 150 GB/s per direction. Each node also has four InfiniBand NDR200 adapters, about 25 GB/s per GPU.

Ava：在节点内部，GPU 通过 NVLink 4 连接，每个方向的带宽为 150 GB/s。每个节点还配有 4 个 InfiniBand NDR200 适配器，即每块 GPU 约 25 GB/s。

Brian: So inter-node traffic is the hard boundary. InfiniBand is 36 times slower than the link between a GPU and its own CPU, so communication has to overlap aggressively with computation.

Brian：因此，节点间流量构成了硬性限制。InfiniBand 的速度比 GPU 与其自身 CPU 之间的链路慢 36 倍，所以通信必须与计算进行高度重叠。

Ava: The host-memory side is tight too. JUPITER’s compute nodes use 120 GB per Grace, and after the kernel’s share, about 108 GiB per GPU is usable. Some nodes start jobs with less.

Ava：主机内存一侧也很吃紧。JUPITER 的计算节点每个 Grace 使用 120 GB，在扣除内核占用后，每块 GPU 约有 108 GiB 可用。有些节点启动作业时可用内存还更少。

Brian: Those constraints led to 384-way FSDP, 4-way expert parallelism inside each node, and no pipeline parallelism. The MoE token all-to-all stays on NVLink because it’s hard to overlap.

Brian：这些限制促成了 384 路 FSDP、每个节点内 4 路专家并行，以及不采用流水线并行。MoE token 的 all-to-all 通信留在 NVLink 上，因为它很难与计算重叠。

Ava: Without pipeline parallelism, steps tend to be shorter, and the team amortized fixed costs with a batch of 384 sequences of 65,536 tokens, about 25 million tokens per step.

Ava：由于不采用流水线并行，每个步骤往往更短；团队用包含 384 个长度为 65,536 个 token 的序列的批次来摊销固定开销，即每步约 2,500 万个 token。

Brian: FSDP already overlaps the gather of layer n+1 with computation of layer n, so the remaining work is to make that overlap effective.

Brian：FSDP 已经将第 n+1 层的 gather 与第 n 层的计算重叠，因此剩下的工作是让这种重叠真正发挥作用。

Ava: The first major optimization is FlexShard for Muon. Muon is used for about 99.5% of the parameters, while AdamW handles the router and embeddings.

Ava：第一项重大优化是针对 Muon 的 FlexShard。Muon 负责约 99.5% 的参数，而 AdamW 处理路由器和嵌入层。

Ava: Why does Muon create a communication problem?

Ava：为什么 Muon 会造成通信问题？

Brian: Muon runs Newton-Schulz iterations on a whole matrix. If FSDP splits each matrix into 384 shards, a simple implementation gathers the matrix on one rank, computes there, and scatters it back. On this interconnect, that communication is too expensive.

Brian：Muon 会在整个矩阵上执行 Newton-Schulz 迭代。如果 FSDP 将每个矩阵拆成 384 个分片，简单实现会在一个 rank 上收集整个矩阵，在那里计算，再将其分散回去。在这种互连网络上，这种通信代价太高。

Ava: FlexShard changes the ownership pattern.

Ava：FlexShard 改变了所有权模式。

Brian: Exactly. Experts are sharded by whole expert, so each rank owns complete expert matrices and runs Newton-Schulz with no communication. Dense matrices still move to an owning rank, while each rank processes its experts during that transfer, overlapping communication with computation.

Brian：没错。专家以完整专家为单位进行分片，因此每个 rank 都拥有完整的专家矩阵，并且无需通信即可运行 Newton-Schulz。密集矩阵仍会移动到负责的 rank，而每个 rank 在传输期间处理自己的专家，从而让通信与计算重叠。

Ava: The optimizer initially ran on Grace because parameters were CPU-offloaded. That took about 35 seconds per step for Newton-Schulz on 72 Arm cores.

Ava：优化器最初运行在 Grace 上，因为参数被卸载到 CPU。在 72 个 Arm 核心上执行 Newton-Schulz 每步大约需要 35 秒。

Brian: They added GPU execution while keeping parameters offloaded. The optimizer step fell from 41.7 seconds to 2.2 seconds, and throughput rose from 441 to 597 tokens per second per GPU, a 35% increase.

Brian：他们加入了 GPU 执行，同时继续将参数卸载到 CPU。优化器步骤耗时从 41.7 秒降至 2.2 秒，吞吐量从每块 GPU 每秒 441 个 token 提升到 597 个 token，增加了 35%。

Ava: The next lever is activation memory. At 65,536 tokens, boundary activations for 74 layers take about 55 GiB per GPU, so they don’t fit beside the weights in HBM.

Ava：下一个发力点是激活内存。在 65,536 个 token 的长度下，74 层的边界激活值在每块 GPU 上占用约 55 GiB，因此无法与权重一起放入 HBM。

Brian: TorchTitan’s FullAC stores activations only at layer boundaries and recomputes the work inside each layer during backward. Since the GPU was idle for much of the baseline step, the extra compute didn’t lengthen it, and throughput rose from 90 to 370 tokens per second per GPU at 32,768 tokens.

Brian：TorchTitan 的 FullAC 只在层边界存储激活值，并在反向传播期间重新计算每层内部的工作。由于基线步骤的大部分时间 GPU 都处于空闲状态，额外计算没有延长步骤时间；在 32,768 个 token 的长度下，吞吐量从每块 GPU 每秒 90 个 token 提升到 370 个 token。

Ava: At the longer sequence length, they offloaded boundary activations to Grace over the 900 GB/s NVLink-C2C link. Each activation moves to Grace after forward, then returns to Hopper one layer before backward recomputation.

Ava：在更长的序列长度下，他们通过 900 GB/s 的 NVLink-C2C 链路将边界激活值卸载到 Grace。每个激活值在前向传播后移到 Grace，然后在反向重计算前一层时返回 Hopper。

Brian: That offload raised throughput from 370 to 508 tokens per second per GPU, a 37% increase. The sequence length reached 49,152 tokens and then 65,536 with Muon.

Brian：该卸载使吞吐量从每块 GPU 每秒 370 个 token 提升到 508 个 token，增加了 37%。序列长度先达到 49,152 个 token，随后在使用 Muon 时达到 65,536 个 token。

Ava: The final optimization in this episode is about allocator fragmentation in FSDP’s streams.

Ava：本集的最后一项优化针对的是 FSDP 各个流中的分配器碎片化。

Brian: After a software-stack upgrade, the CUDA caching allocator retried allocations on every rank at about 70% memory utilization. Even with 25 to 30 GiB free, it couldn’t find a usable block.

Brian：软件栈升级后，CUDA caching allocator 在每个 rank 上、内存利用率约为 70% 时重试分配。即使还有 25 到 30 GiB 的空闲内存，它也找不到可用的内存块。

Ava: The reason was that FSDP uses one compute stream and four side streams, with a separate allocator pool per stream. Memory freed by one stream can only be reused by that stream.

Ava：原因在于 FSDP 使用一个计算流和 4 个辅助流，并且每个流都有独立的分配器池。一个流释放的内存只能由该流重新使用。

Brian: At peak memory, side streams held 27.3 GiB, but only 6.4 GiB was in use. The remaining 20.9 GiB was unreachable from the compute stream, which then couldn’t find a 4 GiB block for an MoE buffer.

Brian：在内存峰值时，辅助流持有 27.3 GiB，但实际只使用了 6.4 GiB。剩余的 20.9 GiB 无法从计算流访问，因此计算流找不到用于 MoE 缓冲区的 4 GiB 内存块。

Ava: How did they fix that without changing the model parallelism?

Ava：他们如何在不改变模型并行方式的情况下修复这个问题？

Brian: They used FSDP2’s unshard_async_op flag, which runs the all-gather setup on the compute stream while NCCL uses its internal stream. Gather buffers then come from the compute stream’s pool. The custom gather was made asynchronous, so the compute stream waits for the network only when it needs the weights.

Brian：他们使用了 FSDP2 的 unshard_async_op 标志，该标志让 all-gather 准备工作在计算流上运行，同时 NCCL 使用其内部流。这样，gather 缓冲区就来自计算流的内存池。自定义 gather 被改为异步执行，因此计算流只有在需要权重时才等待网络。

Ava: That removed allocator retries on all 384 ranks. Peak reserved memory fell from 88.1 to 74.6 GiB, and throughput rose from 996 to 1,210 tokens per second per GPU.

Ava：这消除了全部 384 个 rank 上的分配器重试。峰值保留内存从 88.1 GiB 降至 74.6 GiB，吞吐量从每块 GPU 每秒 996 个 token 提升到 1,210 个 token。

Brian: The flag is being moved into a public FSDP API, so this fix can help other FSDP users too.

Brian：这个标志正被移入公开的 FSDP API，因此这一修复也能帮助其他 FSDP 用户。

Ava: The team also upstreamed a shared RoPE cache, skipped embedding re-gather in backward, added configurable seed-offset mesh axes, fixed CPU initialization resetting the RNG state, and fixed trunc_normal_ all-gathering DTensors.

Ava：团队还向上游贡献了共享的 RoPE 缓存，跳过了反向传播中的嵌入重新 gather，加入了可配置的种子偏移网格轴，修复了 CPU 初始化重置 RNG 状态的问题，并修复了 trunc_normal_ 对 DTensor 进行 all-gather 的问题。

Brian: The resulting setup sustains about 1,300 tokens per second per GPU on 384 GH200s per data-parallel replica. With four replicas, that’s 1,536 GPUs, and the model fits by using both HBM and Grace memory.

Brian：最终配置在每个数据并行副本使用 384 个 GH200 时，可持续达到每块 GPU 每秒约 1,300 个 token。使用 4 个副本时，共有 1,536 块 GPU；模型通过同时使用 HBM 和 Grace 内存得以装下。

Ava: So the takeaway is a stack of targeted changes: place Muon’s shards to avoid communication, move activation checkpoints to Grace, and keep FSDP’s gather allocations on the compute stream.

Ava：所以要点是一组有针对性的改动：安排 Muon 分片以避免通信，将激活检查点移到 Grace，并让 FSDP 的 gather 分配留在计算流上。

Brian: Together, those changes show that shared public infrastructure can sustain frontier-scale training when the software gives engineers control over memory, communication, and execution.

Brian：这些改动结合起来表明，只要软件让工程师能够控制内存、通信和执行，共享公共基础设施就能支撑前沿规模的训练。

Ava: At trillion-parameter scale, system details decide whether the training run is practical. Thanks for listening.

Ava：在万亿参数规模下，系统细节决定训练任务是否可行。感谢收听。

术语

Term · 释义

Mixture-of-Experts (MoE) · 混合专家模型；每个 token 只激活部分专家参数。

FSDP · Fully Sharded Data Parallel，把参数、梯度和优化器状态分片到多个 rank。

FlexShard · TorchTitan 中控制参数归属和分片方式的机制，用于减少 Muon 通信。

Muon · 用于大部分权重矩阵的优化器，需要对更新执行 Newton-Schulz 正交化迭代。

AdamW · 用于 router 和 embedding 参数的优化器。

Newton-Schulz · 对整个矩阵执行的正交化迭代过程。

activation checkpointing · 只保存部分激活，并在反向传播时重算其余激活。

activation offloading · 把激活从 GPU HBM 移到 Grace CPU 内存，以节省显存。

unshard_async_op · FSDP2 的异步 unshard 选项，让 all-gather 设置在 compute stream 上执行。

HBM · GPU 高带宽内存。

Grace CPU · GH200 Superchip 中与 Hopper GPU 配对的 CPU。

NVLink-C2C · 连接 Grace CPU 和 Hopper GPU 的高速互连。

InfiniBand · 节点间网络互连；文中带宽远低于 GPU 与本机 CPU 的连接。

expert parallelism · 按专家划分 MoE 计算和参数的并行方式。

DDP replica · 数据并行副本；每个副本包含一组用于训练的 GPU。

中文内容总结

EUROPA 联盟在 EuroHPC Frontier AI Grand Challenge 中，使用 PyTorch 和 TorchTitan 于欧洲公共超级计算机 JUPITER 上训练近一万亿参数的 Mixture-of-Experts 模型。团队针对 GH200 节点的内存容量和跨节点带宽限制进行定制优化，使 384 张 GH200 GPU 上的吞吐量从每 GPU 90 tokens/s 提升到约 1,300 tokens/s，并将相关改进回馈到 PyTorch 与 TorchTitan。

项目目标与模型

该项目旨在证明共享的欧洲公共计算资源能够支持主权、开源且达到前沿规模的 AI 训练。入选方案要求模型至少包含 400B 参数、支持欧盟 24 种官方语言，并遵守 EU AI Act。实验模型共有 951.9B 参数，每个 token 激活 32.8B 参数，包含 74 层、6,144 隐藏维度、384 个路由专家并采用 top-8 路由，词表大小为 256,000，预训练序列长度为 65,536，优化器使用 Muon 和 AdamW。

JUPITER 的硬件瓶颈与并行布局

JUPITER 的每个 Booster 节点包含 4 个 NVIDIA GH200，每个 GPU 有 96GB HBM3，并通过 900GB/s 的 NVLink-C2C 连接一颗 72 核 Grace CPU 和 120GB LPDDR5X 内存。节点内 GPU 通过 NVLink 4 互联，节点间通信依赖每 GPU 约 25GB/s 的 InfiniBand，带宽比 GPU 与本地 CPU 的链路低 36 倍。计算节点的主机内存小于部分登录节点，且作业启动时可用容量还可能更低，因此模型、梯度和优化器状态必须共同利用 HBM 与 Grace 内存。团队采用 384 路 FSDP、节点内 4 路专家并行，不使用流水线并行，并以 384 条 65,536 token 序列组成约 2,500 万 token 的大批次。

三项关键优化

FlexShard 让每个 rank 按完整专家分片保存参数，使 Muon 的 Newton-Schulz 正交化在专家矩阵上无需跨节点通信；稠密矩阵仍可在传输期间与专家计算重叠。团队还把激活检查点从 Hopper HBM 卸载到 Grace，在反向计算前再传回，从而支持更长序列。针对 FSDP 通信缓冲区被不同 CUDA 流缓存、导致可用 HBM 被碎片化的问题，团队启用 FSDP2 的 unshard_async_op，让 all-gather 设置在计算流上完成，同时让 NCCL 使用内部流。

实测收益与运行条件

在 CPU offload 场景中，团队将 Newton-Schulz 从 Grace CPU 移到 GPU，优化器步骤由 41.7 秒降至 2.2 秒，吞吐量从 441 提升到 597 tokens/s/GPU，增幅为 35%。在 32,768 token 序列上，完整激活检查点使吞吐量从 90 提升到 370 tokens/s/GPU；再加入 Grace 激活卸载后达到 508 tokens/s/GPU，增幅为 37%，序列长度随后扩展到 49,152，并在加入 Muon 后达到 65,536。调整 FSDP 流后，384 个 rank 的分配器重试降为零，峰值保留内存从 88.1 GiB 降至 74.6 GiB，吞吐量从 996 提升到 1,210 tokens/s/GPU。最终报告的持续吞吐量约为 1,300 tokens/s/GPU，运行规模为每个 DDP 副本 384 张 GH200、96 个节点，4 个副本合计 1,536 张 GPU。

限制、开源贡献与实践意义

这些结果依赖 JUPITER 的 GH200 架构、节点内高速互联、有限的 Grace 内存，以及长序列和大批次带来的计算与通信重叠，不能直接视为所有集群都能达到的性能。MoE token all-to-all 仍难以隐藏，跨节点流量和主机内存容量继续限制扩展；数据与专家负载均衡、InfiniBand 流量削减、节点本地重分片、SonicMoE 动态调度和 NCCL SM 使用限制等优化另有配套说明。团队已向 TorchTitan 加入共享 RoPE 缓存、可配置卸载和种子偏移等功能，并修复 PyTorch 的 CPU 初始化随机状态重置和 DTensor all-gather 问题。文章据此主张，经过针对硬件的细粒度软件优化，公共欧洲基础设施可以承载前沿规模训练。
