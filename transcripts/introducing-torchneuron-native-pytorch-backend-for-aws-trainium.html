TorchNeuron: PyTorch Meets AWS Trainium

原文：[Introducing TorchNeuron: Native PyTorch backend for AWS Trainium - PyTorch](https://pytorch.org/blog/introducing-torchneuron-native-pytorch-backend-for-aws-trainium/)

摘要

TorchNeuron 把 AWS Trainium 接入为原生 PyTorch 设备，目标是让研究者沿用熟悉的模型代码、库和工具。节目解释了 eager、实验性的 adaptive eager 与 torch.compile 如何运行，以及分布式 API、自定义 NKI 算子和性能分析工具如何配合。文章报告了大规模模型测试和一项客户基准测试，但没有给出所有模型都能运行的结论。首个版本仍有算子覆盖和动态形状等限制，项目计划于二〇二六年十月二十日以公开测试版发布。

对话

Ava: What if moving a PyTorch training loop to a different AI chip took one device change? That could save a lot of engineering time.

Ava：如果把 PyTorch 训练循环迁移到另一种 AI 芯片，只需要改一处设备设置呢？那能省下大量工程时间。

Brian: That's the promise behind TorchNeuron. It makes AWS Trainium, a family of chips for AI training and inference, a native PyTorch device.

Brian：这正是 TorchNeuron 所承诺的。它让用于 AI 训练和推理的芯片系列 AWS Trainium 成为 PyTorch 原生设备。

Ava: Why does native support matter? People have already been running models on Trainium.

Ava：原生支持为什么重要？人们不是已经在 Trainium 上运行模型了吗？

Brian: They have. But models, libraries, and training tools keep changing. Teams want to use familiar PyTorch workflows without adapting their software each time.

Brian：确实如此。但模型、库和训练工具一直在变化。团队希望沿用熟悉的 PyTorch 工作流程，不必每次都调整自己的软件。

Ava: So the cost isn't just how long a model runs. It's also the work of getting it running.

Ava：所以成本不只是模型运行要花多久，还包括让它跑起来所需的工作。

Brian: Right. The article includes the time spent making a workload work, tuning it, and maintaining it as models and libraries evolve.

Brian：对。文章把让工作负载跑起来、进行调优，以及随着模型和库的发展持续维护所花的时间也算了进去。

Ava: What changed in PyTorch to make this possible?

Ava：PyTorch 发生了什么变化，才让这成为可能？

Brian: PyTorch made many APIs accelerator-agnostic. That means code can address a device through common interfaces. It also added official ways to register custom hardware.

Brian：PyTorch 让许多 API 不再依赖特定加速器。这意味着代码可以通过通用接口指定设备。它还增加了注册自定义硬件的官方方式。

Ava: And TorchNeuron uses one of those ways?

Ava：TorchNeuron 用的就是其中一种方式？

Brian: Yes. PrivateUse1 is PyTorch's extension point for a custom device backend. TorchNeuron registers Trainium there under the device name neuron.

Brian：是的。PrivateUse1 是 PyTorch 为自定义设备后端提供的扩展点。TorchNeuron 在那里注册 Trainium，设备名称是 neuron。

Ava: Give me the simplest example. What does the developer actually change?

Ava：举个最简单的例子吧。开发者实际要改什么？

Brian: In the article's training loop, they move the model to the neuron device. The optimizer and the rest of that loop stay in familiar PyTorch form.

Brian：在文章的训练循环里，开发者把模型移到 neuron 设备上。优化器和循环的其余部分仍保持大家熟悉的 PyTorch 写法。

Ava: That's pleasantly boring. Does device-independent code need even that change?

Ava：这倒是简单得让人开心。已经写成与设备无关的代码，连这一步也不用改吗？

Brian: Code already written against torch dot accelerator, PyTorch's recommended device-agnostic API, can run unmodified. That's useful when a project supports several devices.

Brian：如果代码已经使用 PyTorch 推荐的设备无关 API torch.accelerator，就可以不加修改地运行。当一个项目支持多种设备时，这很有用。

Ava: Okay, the model is on Trainium. How does an operation run?

Ava：好，模型已经在 Trainium 上了。一个算子是怎么运行的？

Brian: There are two main modes: eager execution and torch dot compile. Eager runs operations as Python reaches them. Compile captures work into a graph for optimization.

Brian：主要有两种模式：即时执行和 torch.compile。即时执行会在 Python 运行到某个操作时执行它；编译模式则把操作捕获成计算图，以便优化。

Ava: So eager is the mode where I can still print values and use breakpoints?

Ava：所以在即时执行模式下，我仍然可以打印数值、使用断点？

Brian: Exactly. Python control flow works there too. That's why the article presents eager as the natural choice for research and debugging.

Brian：没错。Python 的控制流在这个模式下也能正常工作。所以文章把即时执行视为研究和调试的自然选择。

Ava: But running every operation separately sounds expensive.

Ava：但每个操作都单独运行，听起来开销很大。

Brian: It can be. Each eager operation compiles its own Neuron Executable File Format file, or NEFF, and launches on the device. Intermediate data moves through device memory.

Brian：可能确实如此。即时执行中的每个操作都会编译出自己的 Neuron Executable File Format 文件，也就是 NEFF，然后在设备上启动运行。中间数据会经由设备内存传递。

Ava: Is that why there's an adaptive eager mode?

Ava：所以才有自适应即时执行模式？

Brian: Yes. It's experimental. The goal is to reduce launch cost and create more chances to fuse operations, while keeping the interactive eager experience.

Brian：对。它还处于实验阶段。目标是在保留即时执行交互体验的同时，降低启动开销，并创造更多融合操作的机会。

Ava: Fuse as in combine several small jobs into one larger job?

Ava：这里的融合，是指把几个小任务合成一个大任务？

Brian: That's the idea. Imagine carrying groceries one item at a time. Combining trips can help, and you still get to work in an interactive way.

Brian：就是这个意思。想象一下搬杂货时每次只拿一件。把几趟合并起来会更省事，而你仍然可以用交互式的方式工作。

Ava: Then when would I choose torch dot compile?

Ava：那我什么时候该选择 torch.compile？

Brian: For a stable model where production performance matters. It captures a graph of operations, lets the Neuron compiler optimize it, and produces a NEFF for the hardware.

Brian：当模型已经稳定，而且生产环境的性能很重要时。它会捕获操作的计算图，让 Neuron 编译器优化，然后生成供硬件执行的 NEFF。

Ava: Do I have to compile the whole model?

Ava：我必须编译整个模型吗？

Brian: No. The article says you can optimize all or part of it, and compiled work can run alongside eager work.

Brian：不用。文章说，你可以优化整个模型，也可以只优化一部分；编译后的操作还能与即时执行的操作一起运行。

Ava: What happens between PyTorch code and that final device file?

Ava：从 PyTorch 代码到最终的设备文件，中间会经过什么？

Brian: TorchDynamo captures an FX graph, a graph representation of the model. AOTAutograd traces the backward graph ahead of time. Torch-MLIR and StableHLO sit on the path to the Neuron compiler.

Brian：TorchDynamo 会捕获 FX 计算图，也就是模型的图表示。AOTAutograd 会提前追踪反向传播计算图。通往 Neuron 编译器的路径上还会经过 Torch-MLIR 和 StableHLO。

Ava: That's a lot of stages. What's the useful picture to keep in mind?

Ava：阶段可真不少。最值得记住的整体过程是什么？

Brian: PyTorch gathers the work, prepares the forward and backward paths, then passes them through compiler stages until Trainium can execute them. That's the key point.

Brian：PyTorch 收集要执行的操作，准备好前向和反向路径，再让它们经过各个编译阶段，直到 Trainium 能够执行。这是关键。

Ava: And how does someone select the Neuron compiler?

Ava：那要怎么选择 Neuron 编译器？

Brian: They can set neuron as the default backend once, or name it in a torch dot compile call. The article shows both choices.

Brian：可以把 neuron 设置为默认后端，设置一次即可；也可以在调用 torch.compile 时指定它。文章展示了这两种方式。

Ava: Does native support reach normal PyTorch features, or just model execution?

Ava：原生支持也覆盖普通的 PyTorch 功能，还是只支持执行模型？

Brian: It reaches familiar interfaces for tensors, neural network modules, automatic mixed precision, distributed work, and profiling. The article also reports broad operator coverage.

Brian：张量、神经网络模块、自动混合精度、分布式计算和性能分析，都有大家熟悉的接口。文章还提到算子覆盖范围很广。

Ava: Broad sounds useful, but it doesn't mean every operator.

Ava：覆盖范围广很有用，但不代表每个算子都支持。

Brian: Correct. We'll get to the gaps. For supported models, the article lists common floating-point types, integer and boolean types, and working mixed precision code.

Brian：没错。我们稍后会谈到这些缺口。对于受支持的模型，文章列出了常见的浮点类型、整数和布尔类型，以及能够正常运行的混合精度代码。

Ava: What about training across many devices?

Ava：在许多设备上一起训练呢？

Brian: The standard distributed APIs are supported. That includes DDP, or Distributed Data Parallel, and FSDP2, or Fully Sharded Data Parallel version two.

Brian：标准的分布式 API 也受支持，包括 DDP，即 Distributed Data Parallel，以及 FSDP2，即 Fully Sharded Data Parallel 第 2 版。

Ava: Can people combine those ideas with tensor and pipeline parallelism?

Ava：能把这些方法与张量并行和流水线并行结合起来吗？

Brian: Yes. The article describes tensor parallelism, pipeline parallelism, and combinations such as FSDP2 with tensor parallelism. DTensor and DeviceMesh help manage sharding and process groups.

Brian：可以。文章介绍了张量并行、流水线并行，以及 FSDP2 与张量并行这样的组合。DTensor 和 DeviceMesh 有助于管理分片和进程组。

Ava: And the devices still need to exchange data.

Ava：设备之间还是需要交换数据。

Brian: Right. Collective operations include gathering and reducing data across workers. Within a node, they use Trainium's dedicated collective cores. Between nodes, they use Elastic Fabric Adapter.

Brian：对。集合通信操作包括在各工作进程之间汇集和归约数据。在节点内部，它们使用 Trainium 专用的集合通信核心；在节点之间，则使用 Elastic Fabric Adapter。

Ava: What if a project uses streams to overlap work?

Ava：如果项目用流来让不同工作重叠执行呢？

Brian: Streams and events are supported. A stream keeps its own operations ordered. If one stream needs another stream's result, you record an event and wait for it.

Brian：流和事件都受支持。同一个流中的操作会保持顺序。如果一个流需要另一个流的结果，就记录一个事件并等待它。

Ava: Like handing over a ticket before the next worker starts?

Ava：就像把票据交过去，下一个工人才开始干活？

Brian: Exactly. There's a hardware detail, though: non-default streams share one hardware queue. They keep ordering and event behavior, but don't each get a dedicated engine.

Brian：正是如此。不过有个硬件层面的细节：非默认流共用一个硬件队列。它们仍然保持操作顺序和事件行为，但不会各自拥有一个专用执行引擎。

Ava: So the PyTorch behavior is there, but I shouldn't picture a separate engine for every stream.

Ava：所以 PyTorch 的行为是有的，但我不该把每个流都想成有一台独立的执行引擎。

Brian: You've got it. And an asynchronous error appears at the next synchronization point. TorchNeuron tracks the earliest exception and reports it with its original context.

Brian：你理解对了。异步错误会在下一个同步点显现。TorchNeuron 会跟踪最早发生的异常，并连同它最初的上下文一起报告。

Ava: Suppose the standard operations aren't fast enough for one critical layer. What's available?

Ava：假设某个关键层用标准算子还不够快，有什么办法？

Brian: NKI, the Neuron Kernel Interface, lets developers write custom operators with lower-level hardware control. Those operators can work in eager and compiled models.

Brian：NKI，即 Neuron Kernel Interface，让开发者能够编写自定义算子，并在更底层控制硬件。这些算子既可用于即时执行模型，也可用于编译后的模型。

Ava: Does that mean rewriting the entire model as custom kernels?

Ava：这是不是意味着要把整个模型都改写成自定义内核？

Brian: No. The article suggests using NKI for performance-critical pieces. It also describes NKI-lib, an open-source set of optimized operators for common language and multimodal workloads.

Brian：不用。文章建议把 NKI 用在性能关键的部分。文章还介绍了 NKI-lib，这是一个开源的优化算子集合，面向常见的语言和多模态工作负载。

Ava: There's a sine example in the article. What should I take from it?

Ava：文章里有个正弦函数的例子。我该从中了解什么？

Brian: It registers a custom sine operator and its backward calculation using PyTorch's recommended autograd registration style. The forward and backward paths call NKI kernels.

Brian：这个例子按 PyTorch 推荐的自动求导注册方式，注册了一个自定义正弦算子及其反向计算。前向和反向计算都会调用 NKI 内核。

Ava: Nice. Once it's running, how do I find the slow part?

Ava：明白了。模型运行起来后，我怎么找出慢在哪里？

Brian: TorchNeuron extends the standard torch dot profiler interface with Neuron-specific settings. It can collect framework, runtime, and device activity in a connected trace.

Brian：TorchNeuron 在标准的 torch.profiler 接口上扩展了 Neuron 专用设置。它能在一份关联的追踪记录中收集框架、运行时和设备的活动。

Ava: Connected how? Profiling tools sometimes give me three timelines that don't seem to know each other.

Ava：是怎么关联的？有些性能分析工具会给我三条时间线，看起来彼此毫无关联。

Brian: Neuron Explorer links events across those layers and back to source lines. It also shows call hierarchy and dependency chains, so you can inspect what a stall is waiting on.

Brian：Neuron Explorer 能把这些层级的事件关联起来，并追溯到源代码行。它还会展示调用层级和依赖链，方便你查看停顿是在等待什么。

Ava: Can an engineer analyze the data without the visual interface?

Ava：工程师能不用可视化界面分析这些数据吗？

Brian: Yes. Neuron Explorer emits Parquet metrics for operations and engines, and the built-in profiler tools can sort operations by device-side cost.

Brian：能。Neuron Explorer 会输出算子和执行引擎的 Parquet 格式指标，内置的性能分析工具也能按设备端开销对算子排序。

Ava: Let's move from features to evidence. What has the team tested?

Ava：先不谈功能，来看看证据。团队测试了什么？

Brian: They report a continuous sweep of one hundred thousand Hugging Face models. Based on download counts, those models cover ninety-nine point nine percent of real-world usage.

Brian：他们称，团队持续扫描了 100000 个 Hugging Face 模型。按下载量计算，这些模型覆盖了实际使用量的 99.9%。

Ava: What did they check for each model?

Ava：他们对每个模型检查了什么？

Brian: Whether it loaded, ran forward and backward passes, compiled, and used device operators or fell back to the host processor. They used reduced but representative configurations.

Brian：他们检查模型能否加载、执行前向和反向计算、完成编译，以及使用的是设备算子还是回退到主机处理器。测试采用了规模缩减但具有代表性的配置。

Ava: Does the article say every model passed?

Ava：文章说所有模型都通过了吗？

Brian: No. It says the team is closing remaining gaps. The supplied text refers to a graph of sweep results, but doesn't give a pass percentage to quote.

Brian：没有。文章说团队正在弥补剩余的缺口。提供的文本提到一张展示扫描结果的图，但没有给出可引用的通过率。

Ava: Was there testing against PyTorch itself?

Ava：他们还针对 PyTorch 本身做了测试吗？

Brian: Yes. The August twenty twenty-six run had about one hundred fifty-four thousand upstream test outcomes. Roughly sixty-nine thousand were skipped for stated reasons.

Brian：做了。2026 年 8 月的那次测试产生了约 154000 个上游测试结果。其中约 69000 个因已说明的原因被跳过。

Ava: That's a large skipped group. What was in it?

Ava：跳过的测试数量很大。里面包括哪些？

Brian: About thirty thousand came from PyTorch's own eligibility checks. Around thirty-nine thousand were deliberate Neuron skips, including about twenty-two thousand tied to missing native operator lowering.

Brian：约 30000 个是由 PyTorch 自身的适用性检查筛掉的。约 39000 个是 Neuron 有意跳过的，其中约 22000 个与缺少原生算子转换支持有关。

Ava: So those totals alone don't tell us a pass rate.

Ava：所以，光看这些总数算不出通过率。

Brian: Right. The article says it reports pass rates against enabled tests, but these counts need their skip categories to make sense.

Brian：对。文章说通过率是按已启用的测试计算的，但要理解这些数量，还得看各类跳过原因。

Ava: Are there any customer performance numbers?

Ava：有没有客户提供的性能数据？

Brian: Deepgram reports that, in the benchmarks it evaluated, Trainium processed about sixty percent more input audio seconds per dollar than its existing graphics processing unit, or GPU, baselines.

Brian：Deepgram 报告称，在其评估的基准测试中，与现有图形处理器（GPU）基线相比，Trainium 每花费 1 美元处理的输入音频时长多了约 60%。

Ava: That's specific to Deepgram's benchmarks, then.

Ava：也就是说，这个结果只针对 Deepgram 的基准测试。

Brian: Yes. Cartesia offers a different example: it says its standard inference pipeline ran with minimal PyTorch code changes, leaving it to focus custom kernels on repeatedly used layers.

Brian：对。Cartesia 提供了另一个例子：它说自己的标准推理流水线只需对 PyTorch 代码做少量修改就能运行，因此可以集中精力为反复使用的层开发自定义内核。

Ava: How does this connect to libraries people already use?

Ava：这和大家已经在用的库有什么关系？

Brian: The article describes Trainium support in TorchTitan and upstream Hugging Face libraries, including Transformers and Diffusers. Those connections are central to the compatibility goal.

Brian：文章介绍了 TorchTitan 和 Hugging Face 上游库中的 Trainium 支持，包括 Transformers 和 Diffusers。这些集成是实现兼容性目标的关键。

Ava: What's still missing in this first release?

Ava：首个版本还有哪些地方没做好？

Brian: Some operators lack native lowering. The explicit first-release exclusions include sparse tensors, forward-mode autograd, and dynamic and symbolic shapes. The team says it's working on coverage.

Brian：有些算子还缺少原生转换支持。首个版本明确不支持稀疏张量、前向模式自动求导，以及动态形状和符号形状。团队表示正在扩大支持范围。

Ava: And what's next for availability?

Ava：接下来什么时候能用上？

Brian: The article announces an open-source public beta under Apache two point zero for October twentieth, twenty twenty-six, with installable packages. It also says TorchAO and FP8 are in private beta for now.

Brian：文章宣布，将于 2026 年 10 月 20 日推出采用 Apache 2.0 许可证的开源公开测试版，并提供可安装的软件包。文章还说，TorchAO 和 FP8 目前仍处于非公开测试阶段。

Ava: Give me the three things to remember.

Ava：给我说说最该记住的 3 点。

Brian: First, TorchNeuron makes Trainium a native PyTorch device. Second, eager, compile, custom kernels, and profiling give teams several ways to work. Third, the testing is broad, but first-release gaps remain.

Brian：第一，TorchNeuron 让 Trainium 成为 PyTorch 的原生设备。第二，即时执行、编译、自定义内核和性能分析，为团队提供了多种使用方式。第三，测试覆盖面很广，但首个版本仍有功能缺口。

Ava: That's our tour of TorchNeuron. Thanks for listening.

Ava：以上就是我们对 TorchNeuron 的介绍。感谢收听。

中文内容总结

TorchNeuron 是面向 AWS Trainium2 和 Trainium3 的开源 PyTorch 后端，计划于 2026 年 10 月 20 日以 Apache 2.0 许可证发布公开测试版。它把 Trainium 注册为标准设备，让现有模型、训练和推理工具尽量沿用 PyTorch 工作流。

接入与执行机制

TorchNeuron 使用 PyTorch 的 PrivateUse1 和 torch.accelerator 扩展接口。模型可通过 .to('neuron') 移至设备；使用 torch.accelerator 的代码可沿用原有设备选择方式。即时执行模式支持 Python 控制流和断点，但逐算子编译、启动及传递中间结果会增加开销。实验性的自适应即时执行模式旨在减少启动开销并融合操作。生产场景可用 torch.compile 指定 neuron 后端：TorchDynamo 捕获计算图，AOTAutograd 处理反向图，再经 Torch-MLIR、StableHLO 和 Neuron 编译器生成设备执行文件。

开发、并行与分析工具

后端支持常用 PyTorch 算子、自动混合精度、BF16、FP32、FP16，以及 DDP、FSDP2、张量并行和流水线并行等分布式接口；节点间通信使用 EFA。TorchNeuron 也支持流与事件：同一流内按序执行，跨流使用结果前须通过事件显式建立依赖；非默认流共用一条硬件队列，并非各有独立队列。开发者可用 NKI 编写自定义算子，或采用 NKI-lib 中的注意力和 MoE 内核。torch.profiler 可结合 Neuron Explorer 关联框架、运行时和设备事件，定位到源代码行并分析等待链。TorchTitan、Transformers v5、Diffusers 和 TRL 已提供相关支持；vLLM Neuron 与 vLLM Omni Neuron 分别面向语言模型及图像、视频生成服务。

验证与实测

项目持续抽取 10 万个 Hugging Face 模型，以缩小但有代表性的配置检查加载、前后向运行、编译及 CPU 回退；按下载量计算，这批模型覆盖 99.9% 的实际使用量。Deepgram 称，在其评估的基准测试中，Trainium 每美元处理的输入音频秒数比其现有 GPU 基线约多 60%；这一结果来自该公司的特定工作负载和基线。

当前边界与使用条件

2026 年 8 月的 PyTorch 上游测试约产生 15.4 万项结果，其中约 6.9 万项有理由跳过：约 3 万项由 PyTorch 自身的适用性检查排除，约 3.9 万项由 Neuron 主动跳过，后者约 2.2 万项涉及尚无原生实现的算子。首版还不支持稀疏张量、前向自动微分、动态与符号形状等功能；TorchAO 和 FP8 当时仅在私有测试中。迁移现有模型时，仍需核对具体算子、形状和精度路径。
