# PyTorch Monarch 在 AMD GPU 上的弹性训练

依据：原文

来源：https://pytorch.org/blog/bringing-pytorch-monarch-to-amd-gpus-single-controller-distributed-training-on-rocm/

文章介绍将 PyTorch Monarch 移植到 ROCm，使开发者能用单个 Python 程序调度 AMD GPU 集群，并结合 TorchFT 和 TorchTitan，在部分训练进程故障后恢复副本，而不必重启整个训练任务。

### 问题与架构

大模型训练横跨数百或数千块 GPU，显存错误、网络中断或节点崩溃会使整项任务停下。定期保存全量检查点需要大量存储带宽；故障后从检查点重启，还会丢失其后的计算进度。Monarch 用 actor、进程网格和监督树管理集群，将故障限制在局部。TorchFT 负责训练步级别的法定人数协调，TorchTitan 执行训练计算。

### ROCm 移植

团队用 hipify_torch 将集合通信的 C++ 桥接代码转换为 HIP，并接入 RCCL；构建系统按平台选择 HIP 或 CUDA 的 GPU 内存接口。RDMA 路径保留 libibverbs，通过 GPU_PLATFORM=rocm 切换 GPU 侧绑定。由于 ROCm 没有对应的静态 HIP 运行时库，构建改为动态链接 amdhip64；Rust 兼容层则把 HIP 类型和函数映射到原有 CUDA 名称。作者报告 1,171 项测试全部通过，支持 ROCm 7.0 及以上版本。

### 故障恢复流程

示例中，四个副本组各运行八个 GPU 进程，每 20 步进行一次 DiLoCo 梯度同步。一个进程崩溃后，Monarch 捕获错误并在原位置重建该副本的进程网格，其余副本继续训练。Lighthouse 选出健康副本提供模型、优化器、调度器和训练器状态；各副本在形成新法定人数的边界短暂停顿，随后恢复同步。因此，这套方案避免的是全局检查点重载，并非完全不传输检查点状态。

### 验证结果

在 SLURM 管理的 16 节点、128 块 MI300 GPU 集群上，团队训练 Llama 3 8B，每 180 秒注入一次 RCCL 故障。活跃 worker 数量在 8 至 16 之间变化，训练未整体重启，损失曲线与未注入故障的基线接近。在 Kubernetes 管理的 32 节点、256 块 MI355 GPU 集群上，参与者数量在恢复期间约为 30 至 32，平均损失从 12 平稳降至约 4。这些是指定集群与故障注入条件下的观察结果。

### 边界与应用

作者称局部重启可在数秒内完成，只有故障处理升级时才需数分钟；16 节点实验中，没有副本停机超过 30 分钟。但文章未给出各实验实测的具体恢复耗时、吞吐损失或与定期全量检查点方案的量化比较，也未验证其他硬件或故障类型。作者计划扩展网卡支持和训练框架覆盖范围，缩短副本重新加入时的状态加载时间，并让恢复过程与计算更多重叠。
