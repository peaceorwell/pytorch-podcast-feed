用 Flight Recorder 排查 NCCL 看门狗超时

依据：原文

来源：https://pytorch.org/blog/flight-recorder-a-new-lens-for-understanding-nccl-watchdog-timeouts/

NCCL 看门狗超时由 PyTorch 的 c10d 看门狗抛出，表示某个集合通信操作未在期限内完成，并不直接说明 NCCL 库或网络出了故障。报错通常只包含看门狗线程的栈；最先报错的 rank，以及报错时正在执行的集合通信，都未必是根因。PyTorch Flight Recorder（FR）为跨 rank 追查故障保留了更有用的记录。

超时如何产生

CPU 调度集合通信后，GPU 异步执行；c10d 用 Work 对象和前后两个 CUDA 事件跟踪执行状态，由看门狗定期检查，默认超时为 10 分钟。某些 rank 若未按相同顺序调度相同或互补的操作，其他 rank 就可能一直等待。Meta 在其训练任务中观察到，绝大多数超时与集合通信失同步有关，单纯延长超时时间不能解决这类问题。

主要根因及观察范围

CPU 侧卡顿或执行路径分叉会让部分 rank 漏掉或改变集合通信，诱因包括数据加载、检查点保存、PT2 编译耗时差异、数据不均衡及异常处理。GPU 计算核卡住也会阻止后续通信执行；数据类型、张量大小或 all_to_all_single 收发分片配置不一致，则可能使通信一直等待。网络和硬件故障是另一类原因。Meta 报告称，在所观察的训练框架中，CPU 侧问题占比超过 60%，网络或硬件问题占 20% 至 30%；这些是其内部工作负载的观察值。

记录与转储机制

FR 在每个 rank 的 CPU 侧维护环形缓冲区，记录各进程组的集合通信类型、输入输出数据类型和大小、调用栈，以及“未调度、已调度、已在 GPU 启动、已完成”等状态；序列号在各进程组内递增。设置 TORCH_NCCL_DUMP_ON_TIMEOUT 后，超时会触发记录转储。PyTorch 通过 TCPStore 向各 rank 广播信号，由监控线程促成转储，即使故障 rank 的其他线程卡住也尽量保留记录。作者称，这套尽力而为的设计在 Meta 内部实现了接近 100% 的全 rank 完整转储率。

如何定位故障

离线工具 fr_trace 按进程组、调度顺序和元数据对齐各 rank 的记录，列出缺席的 rank、操作类型或参数差异，并给出代表性调用栈。Meta 还用跨 rank 可视化比较通信历史。一个推荐系统案例中，调用栈指出数据相关的条件逻辑让部分 rank 跳过了指标汇总；另一案例中，初看各 rank 似乎都在执行同一次 all_to_all，FR 调用栈却表明卡住的调用分别属于连续两次通信。输入大小配置错误使部分 rank 提前完成第一次并进入下一次，其他 rank 仍在第一次操作中等待。

局限与后续方向

FR 的状态差异只能帮助缩小范围：CPU 卡顿与 GPU 卡顿可能表现相似，网络故障也可能没有明显的跨 rank 不匹配。确认故障仍需结合 CPU 主线程栈、重复故障记录或硬件信号；PyTorch 目前尚未提供配套的主线程栈诊断工具。作者计划将 FR 接入 TorchComm，验证其与 CUDA graphs 等主机侧优化的兼容性，并扩展至 MTIA、Gloo 等后端。
